### Shop search (real defect, fixed)
- Reproduction: in a preview with catalogue products, `GET /shop.php?query=…`
  returned HTTP 500 and logged `PDOException SQLSTATE 0A000` at
  `ProductRepository.php:68`.
- Cause: product names, descriptions and slugs use the nondeterministic ICU
  collation `homas_unicode_ci`; PostgreSQL rejects `LIKE` on it as soon as it
  compares a row. The live catalogue currently has no products, so live
  searches did not fail yet (verified read-only with the pre-fix query); every
  search would have failed once a product was published. ("The collection
  could not be loaded" in the page source is a hidden template, not an error.)
- Fix: `ProductRepository::catalogueFilter()` compares
  `LOWER(column) COLLATE "C" LIKE LOWER(:pattern)`, the pattern already used by
  the admin product, customer and request searches. Escaping is unchanged.
- Regression checks: `verify-application` now passes (customer search, signup,
  sign-in, cart, checkout, account, order privacy, 78 route entry points) and
  checks case-insensitive search and a literal `%`. The same test fails at
  search on the pre-fix source.

### Accessory stock (no defect)
Trash keeps consumed accessories consumed (documented rule since
2026-11-10); Restore deducts only what an order does not already hold
(`needed − held`), and only for orders with a legacy `ORDER_RESTORATION`.
`verify-accessory-stock` now proves: Trash and Restore move nothing for a
prepared order; three more Trash/Restore cycles leave one deduction; a legacy
order takes its boxes back exactly once and is refused when stock is short;
a picked-up order never moves stock. 26 checks pass on current and
pre-refactor code. `AccessoryStockService::restoreForOrder()` is no longer
called by the application (kept: the test uses it to build legacy fixtures).

### Migration checksums (explained; line-ending safeguard applied 2026-11-13)
- Symptom: `verify-migration-upgrade` reports "Applied migration was
  modified: 001_create_catalogue_schema.sql".
- Live database: all 32 recorded checksums match the current migration files
  byte-for-byte, so `scripts/migrate.php` on the live site is not affected.
- Cause: commit 3035b60 converted the MySQL migrations 001–020 to PostgreSQL.
  `app/database/known_comment_only_checksums.php` and this test describe the
  earlier MySQL history (version A `fe00…`/B `7798…` of 001); no PostgreSQL
  database can contain that history, so the simulated upgrade is impossible.
- Hazard found: Git stores the migrations with LF line endings, but the live
  database recorded **001–020 with CRLF bytes and 021–032 with LF bytes**
  (`migrate.php` hashes raw bytes). Any checkout that converts line endings
  differently (a Linux clone, or a Windows clone with `core.autocrlf=true`,
  which would turn 021–023 into CRLF) makes those migrations look "modified"
  and stops `migrate.php`.
- Applied (approved 2026-11-13): `.gitattributes` pins each range to the line
  ending the live database recorded (`eol=crlf` for 001–020, `eol=lf` for the
  rest, including future migrations). No migration file was changed. Verified:
  a simulated fresh checkout (HEAD for 001–023, Git's own add/checkout filters
  for the not-yet-committed 024–032) hashes identically to all 32
  `schema_migrations` records, and `git status` shows the tracked migrations
  clean. An earlier draft of the rule (`eol=crlf` for everything) was wrong
  and was replaced before this check.
- Still proposed, not done: (2) rewrite `verify-migration-upgrade` to simulate an upgrade from a
  PostgreSQL installation that applied 001–N, keeping the rejection of unknown
  checksums; (3) mark the MySQL-era known-checksum table as historical. No
  applied migration, recorded checksum or database row would change.

### Incident logs not writable on the live container (fixed 2026-11-13)
`app/storage/logs` and `application.log` in `homas-test` were owned by root
(mode 755); Apache runs as `www-data` and could not write them, so uncaught
errors since 2026-10-01 were not logged. `scripts/preflight.php` reported the
directory writable only because `docker exec` runs as root.

- Applied (approved): `docker exec homas-test chown -R www-data:www-data
  /var/www/html/app/storage/logs` (the Dockerfile already does this for new
  images). Verified by writing a maintenance line through
  `ErrorBoundary::writeLog()` as `www-data`; it appeared in `application.log`.
- Preflight fixed: when run as root it now checks the owner/group/mode bits
  for the web user (`www-data`, override with `HOMAS_WEB_USER`). Run as root
  and as `www-data`, it now gives identical results.

  keeps the old file names working with 301 redirects. Verified in the demo stack
  for every old name, including a query string. The `public/.htaccess` rules were
  never active because the Apache image sets `AllowOverride None`, so the rule table
  lives in the image configuration instead.
