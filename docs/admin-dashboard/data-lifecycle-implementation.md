# HOM'AS data lifecycle implementation

1. **Entities reviewed.** Customer and administrator accounts, addresses, materials, products (including physical Items/components), categories, product types, colors, scents, promotion codes, custom requests, orders, payments, stock movements, production records and translation review audit records. Items continue to use products and set composition.

2. **Edit actions.** Existing product, material and taxonomy forms are exposed consistently from lists/details. Promotion Edit opens the existing upsert form. Added current customer/admin profile forms, administrator creation, and customer-owned profile/address editing. Administrator accounts are accessible from navigation and Settings.

3. **Delete actions.** The confirmation workflow permits permanent deletion only for unused customers/admins/materials/products/taxonomy/promotion records. Owned translations and reset tokens retain existing cleanup semantics. No independent Item model or second Order Trash implementation was introduced.

4. **Blocked deletion.** All meaningful direct references block permanent deletion, including inactive and trashed relationships. Current/last active administrators are protected. Requests, orders, payments, stock movements and production events have no generic hard-delete action.

5. **Deactivation.** Existing is_active and account_status fields are reused. Referenced master records can be deactivated while history remains readable. Product activation still requires readiness. Customers may suspend their own account after authenticated confirmation; administrator reactivation is required.

6. **Archive/Trash.** Custom requests gain archive/restore and an Archived filter, preserving converted orders and generated catalogue drafts. Existing Order Trash/restore remains. Trash no longer returns consumed accessory stock; recorded material consumption and payments also remain unchanged. Restore supports existing legacy stock-return reconciliation.

7. **Reused services.** AdminProductService, MaterialService, TaxonomyService, ProductReadinessService, PricingService, AccessoryStockService, OrderTrashController, TransactionManager, existing administrator authorization, CSRF/flash/PRG infrastructure and PasswordPolicy.

8. **Required new code.** AdminLifecycleRepository reads actual PostgreSQL FK dependencies and performs allowlisted persistence. AdminLifecycleService adds missing reference-aware deletion/account status/request archive coordination while delegating existing activation rules. AdminLifecycleController validates CSRF and strict identities. AccountProfileService adds missing current-profile edits and customer-owned status handling. No separate pricing, inventory, production or audit framework was added.

9. **Database migration.** New migration 026_protect_business_lifecycle.sql was tested against disposable schemas and applied to the local development database. It adds request archive timestamp/actor, restrictive historical relationships, promotion snapshot concurrency guards, review-actor FK and supporting indexes. Applied migrations 001?025 were unchanged.

10. **Unsafe relationships corrected.** Cascades from orders into lines/status history, lines into recipe snapshots, requests into contact/conversion definitions, and products into composition/configuration/review audit now restrict deletion. SET NULL links that previously erased customer, administrator, product, type, color, scent or material identity now restrict deletion. Translation and reset-token cascades remain owned metadata. The review-actor FK is NOT VALID for existing legacy orphan values; new references and deletes are enforced.

11. **Field restrictions.** Referenced materials cannot change unit, SKU, stock-tracking identity or material type. Referenced category/type slugs and scent-to-material mappings cannot change. Names, descriptions and safe current metadata remain editable. Existing inactive category/type/material selections remain resolvable on edit; new inactive assignments are rejected.

12. **History protections.** Current-profile/catalogue changes do not update historical order contacts, names, options, prices, discounts or recipe snapshots. Historical joins are not filtered by current active state. Payment reviewer and other audit identities remain attached after deactivation. Inventory corrections continue to use movement services.

13. **Dependency checks.** Counts are derived from actual pg_constraint relationships, including orders, recipes, stock, addresses, components, requests, drafts and audit actors. Snapshot-only promotion usage is checked separately. Counts run on detail/confirmation rather than once per list row. The final mutation authorizes, locks the target, recounts references and executes in the existing transaction manager. Administrator decisions are serialized. FK restrictions and promotion row locks reject competing reference insertions.

14. **Confirmation UX.** Lists/details expose Edit and Manage status / deletion; confirmations show record name, lifecycle badge, dependency counts, deactivation/archive consequences and Cancel. Referenced records have no permanent-delete button. Unused deletion is separated in an explicit confirmation disclosure. Mutations require POST, CSRF, strict IDs, authorization and PRG; friendly errors replace FK/SQL details. Existing PostgreSQL-incompatible translation upserts and customer directory LIKE/email-domain queries were corrected where authenticated checks exposed them.

15. **Validation.** 430 assertions passed: lifecycle 95; authenticated manual-order/customer/lifecycle/profile routes 99; order editing 44; payments 20; pricing/recipe snapshots 129; catalogue workflow 43. Tests use disposable schemas, including two actual competing PDO connections for reference/promotion races, forged CSRF/IDs, current administrator protection, inactive discovery, history preservation, prepared-order Trash/restore and customer self-deactivation. PHP syntax and git diff whitespace checks passed. Catalogue verification was changed to isolate its fixtures instead of writing into the main schema.

16. **Browser review.** Chromium-rendered desktop fixture pages were visually inspected for 21 administrator list/detail/edit/confirmation surfaces and the customer-owned profile page. These included active/inactive color and scent rows, a physical component, referenced confirmations and an unused deletion disclosure. HTTP tests exercised the actions. Interactive mouse/keyboard and mobile acceptance review on the real deployment remain. Sites hosting cannot run this existing PHP/PostgreSQL backend directly; the application and hosting model were preserved, and no Sites deployment was made.
